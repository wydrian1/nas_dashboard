# Two-domain dashboard and automatic ZeroSSL (web 1.3.0)

Both `https://wydrian.hu` and `https://nas.wydrian.hu` serve the same dashboard/database with unchanged RBAC. The browser stays on its chosen dashboard host. Google callbacks must be registered for **both** exact `/api/auth/callback/google` HTTPS URLs.

Set `AUTH_MULTI_DOMAIN=true` and remove `AUTH_URL` / `NEXTAUTH_URL` for production activation. Auth.js route requests are normalized to the HTTPS origin validated against the two exact hosts. Lazy session/action configuration also validates trusted proxy headers. Caddy is the public proxy; Next remains loopback-only. No wildcard trusted hosts or shared/domain-wide dashboard session cookies. Each host has its own sign-in/session. The old single-host configuration and local development still work when multi-domain mode is disabled.

Admin-helper mutations require the origin of the request to match the exact dashboard host; accepting both sites does not allow sibling/cross-host mutations. Its four service targets and owner review/confirmation remain unchanged. Android pairing/update/push retains its original `nas.wydrian.hu` endpoint. OpenCode stays on the original dashboard/tool hosts: an owner opening `/opencode` on the apex is sent to `https://nas.wydrian.hu/opencode`. Its original short lease/cookie domain is not broadened; a separate sign-in may be needed there. Original OpenCode is never restarted for this change.

## TLS

The apex uses the **free ZeroSSL ACME** directory `https://acme.zerossl.com/v2/DV90`, EAB authorization and HTTP-01 on public TCP 80. This is not ZeroSSL's potentially paid proprietary certificate API. Caddy manages issuance, storage and automatic renewal, including new private keys as required, in the already encrypted-backup-protected `data/caddy` store. No periodic Windows task or manual certificate replacement is needed. Renewal requires continuing DNS/port-80 reachability, Caddy uptime and intact ACME account/storage; a first issue does not itself prove a future renewal.

The owner-supplied `cert/eam` input consists of two nonempty base64url lines (EAB Key ID, then HMAC key). `node --experimental-strip-types scripts/Prepare-ApexTls.mjs` stores a protected `(zerossl-apex)` Caddy snippet in `.runtime/secrets/zerossl-apex.caddy`, refuses conflicting existing credentials and never prints EAB values. Never log, publish or serve that snippet, adapted Caddy JSON, EAB credentials or TLS private keys. `cert/` is entirely git-ignored and excluded from application build tracing. The supplied certificate/key are preserved as inputs, not installed as an unmanaged certificate that would disable Caddy renewal. The managed ZeroSSL certificate can have a new serial/key. Existing NAS/OpenCode TLS policies remain unchanged.

## Owner-approved port-80 handover

An elevated read-only inspection must confirm IIS has only the expected `Default Web Site` HTTP `*:80:` binding. Preserve its configuration and prior service startup/state. Hand over port 80 by stopping **only W3SVC**, changing its automatic startup to Manual so it cannot reclaim the port on reboot, and adding a Caddy-program-scoped TCP-80 firewall rule if absent. Do not stop WAS, HTTP.sys/PID 4, remove IIS/websites, alter unrelated firewall rules or broaden the deployment/restart helpers.

Changing/restarting HTTPS and IIS is outside the delegated web/worker broker; it needs explicit owner authorization and a scoped UAC-approved activation. Keep a protected copy of the prior Caddy configuration/environment/IIS configuration and rollback state. Validate the exact Caddy configuration before stopping IIS. On failure restore the previous Caddy configuration, W3SVC startup/state and only the firewall rule created by this operation. Original service identities stay unchanged.

After verified HTTPS activation, a separate owner-approved `scripts/Remove-IisAfterApex.ps1` may disable all enabled `IIS-*` Windows optional features. The owner separately authorized complete IIS retirement. This script preserves the configuration and feature inventory, does not disable unrelated Windows features/WAS explicitly, does not remove component payloads, and uses `-NoRestart`. If Windows requires reboot to finish, report it and obtain separate authorization; do not reboot automatically. Reinstall/reenabling IIS is an owner maintenance action, not an automatic broker rollback after retirement.
